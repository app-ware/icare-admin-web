# Authentication, authorization, and security findings

## What authenticates today

`login.aspx.vb:16` sends the submitted username/password directly to `BaseData.GetLoginUser` (`DML.vb:102`), which invokes `authenticateDealer` in the secure database. Parameters include username/password and output isAdmin, dealerID, authenticationStatus. Only authenticationStatus=1 makes the helper return the dealer ID. The page requires a positive ID, adds it to ASP.NET Session, and redirects to Index.

The [database follow-up](07-database-inspection.md) verified SHA2-512(password + GUID salt), BINARY(64) storage and an `is_active=1` check in the secure dealer login. The procedure contains no work factor, failed-attempt lockout or throttling. The application does not implement MFA, a password reset flow, a remembered-device policy or login throttling. Dealer hashing does not establish how other identities store credentials: center-user compatibility code explicitly writes submitted passwords into operational `sec_users.Password` and passes old/new password arguments to the unavailable log database. No password records were read.

Forms authentication is configured in Web.config, but the reviewed code never calls FormsAuthentication.SetAuthCookie/RedirectFromLoginPage or establishes an authenticated claims principal. Page protection relies on Session UserID. Login does not visibly rotate/abandon the prior session. Logout calls Session.Clear, not Session.Abandon or FormsAuthentication.SignOut. Session timeout, storage mode, effective cookie policies, and TLS can be overridden by IIS/machine/proxy configuration and were not tested.

`Extensions.redirectTo` (`Extensions.vb:7`) calls Response.Redirect(..., False) and CompleteRequest. These do not return from the currently executing handler. Guards must not be assumed to stop all later work; this requires careful postback testing.

## Target access model

Authentication establishes a server-verified identity; authorization grants named permissions at a center scope. Candidate permission groups are centers.read/write/create, users.manage, dealers.manage, status.manage, payments.read/write, reports.read/export, alerts.write/reset, transport.manage, integrations.manage, audit.read. This is a **proposed** policy, not inferred permission equivalence.

Every grant needs both a capability and a center scope (or an explicit global grant). Center scope is the composite `{id, type}`; ID collisions across databases must not share access. No role defaults to global access. Super-admin becomes a deliberate set of grants; dealer IDs 4/5 must be mapped to named approved grants rather than hardcoded conditions.

The subsequent [phase-one implementation](08-authentication-and-centers.md) uses this tested default-deny policy with the existing dealer verifier, opaque server sessions, current account/ownership checks and typed SQL center adapters. Its explicitly isolated demo mode cannot select live repositories. It adds no custom password store, browser-trusted live role or silent demo fallback. Restricted TLS SQL configuration and real dealer acceptance remain pending.

## Identity migration decision still required

Prefer OIDC and MFA with opaque server-managed sessions and short idle/absolute limits. Provider selection (existing Microsoft Entra ID, another existing provider, or a dedicated identity service) needs the organization's operational context. The available dealer verifier's definition and disabled-account checks are now reviewed; that alone does not authorize enabling compatibility login. A temporary verifier still needs throttling, current grant/revocation checks, restricted encrypted DB access and a migration plan. Password compatibility must not be inferred from the unused encryption helper.

Center-user identities may also serve other iCare applications. Never bulk replace password encoding, usernames, domains, or account IDs until those consumers are identified. If transition requires a legacy credential verifier, isolate it, rate-limit it, audit it without logging secrets, and plan its removal.
